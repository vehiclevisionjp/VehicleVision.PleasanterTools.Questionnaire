# パスキー 運用手順書

管理画面へ**パスキー（WebAuthn）**で入れるようにする手順（Issue #1082。親は Core#213。画面は #1068 / #1072）。

**既定は無効。** 設定しなければ、これまでどおりパスワード・SAML・Pleasanter のログインだけになる。

仕様（API の経路・不変条件 P1〜P10・監査イベント・失効と復旧）は、Core の
[認証とセッションの仕様書](https://github.com/vehiclevisionjp/VehicleVision.PleasanterTools.Core/blob/v0.3.0/_documents/管理画面の共通仕様/認証とセッションの仕様書.md)
の 3.10 を正とする。**この文書は、本アプリで運用する人が知るべきこと（設定・有効にする手順・本アプリの判断・復旧）だけを書く。**
DB の直接操作（最終手段）は、Core の
[パスキーの運用手順書](https://github.com/vehiclevisionjp/VehicleVision.PleasanterTools.Core/blob/v0.3.0/_documents/管理画面の共通仕様/パスキーの運用手順書.md)
の 5 章を参照し、**この文書の 6.2 の差分（時刻の目盛り）を必ず読む。**

- 実装: `src/VehicleVision.PleasanterTools.Questionnaire.Web/Services/AdminPasskeySettings.cs`（設定の検証）、
  `Services/AdminPasskeyAdapters.cs`（Core.Web の受け口の実装）、`Program.cs`（登録と経路）
- 画面: ログイン画面の「パスキー」タブと、マイアカウントのパスキー管理（`Frontend/src/admin/`。#1072）
- 使っているライブラリ: Core.Web 0.3.0 が推移的に伴う Fido2NetLib（MIT。版・出典は [`NOTICE`](../NOTICE)）

## 1. できること

| 項目 | 内容 |
|---|---|
| ログイン | ログイン画面の「パスキー」タブから、ユーザー名を入れずに入れる（ディスコバラブル資格情報）。**本人確認（UV）を必須**にする |
| 2 要素 | **パスキーで入ったセッションは 2 要素を満たす**（TOTP を求めない）。パスワードの後の 2 要素目には使わない |
| 管理 | マイアカウントで、登録（名前を付ける）・一覧・名前の変更・削除。**登録と削除は、そのたびに再認証**（パスワード、または登録済みのパスキー） |
| 1 人あたりの上限 | 10 件（Core の既定。超えると 409） |
| 復旧 | 管理者が他人のパスキーを全部消せる（API。画面は別 Issue）。対象者の全セッションを失効させる |
| 端末の一覧 | 入った方式に「パスキー」と出る |
| 監査 | 登録・削除・名前の変更・ログインの成功と失敗を、管理操作の記録（監査ログ）へ残す（4 章） |

**パスキーだけで入る人は作らない。** パスワード・SAML・Pleasanter のログインのどれも使えなくなる削除は、409 で断る。

## 2. 設定

**環境変数で指定する（パラメータファイルの別名は用意していない）。画面から変えられない。** 変えたらアプリを再起動する。

| 設定 | 意味 | 既定 |
|---|---|---|
| `QUESTIONNAIRE_ADMIN_PASSKEY` | パスキーを有効にするか（`true` / `false`） | `false`（無効） |
| `QUESTIONNAIRE_ADMIN_PASSKEY_RPID` | RP ID。**ホスト名だけ**（スキーム・ポート・パスは付けない。例 `questionnaire.example.com`） | 未設定 |
| `QUESTIONNAIRE_ADMIN_PASSKEY_ORIGINS` | 許可する Origin。`https://ホスト名[:ポート]`。複数はカンマ区切り | 未設定 |

> **⚠️ Core の手順書は「RP ID・Origin は通常は書かなくてよい（リクエストのホストから決める）」と書くが、本アプリは補わない**
> （Issue #1082 の設計 4/4）。`Host` ヘッダーは偽装でき、偽装されると攻撃者の値が RP ID・Origin になるため。

- **有効（`true`）なのに `_RPID` か `_ORIGINS` が未設定・空なら、起動を止める。** ログには足りない設定名が出る
  （例: `QUESTIONNAIRE_ADMIN_PASSKEY=true のときは、QUESTIONNAIRE_ADMIN_PASSKEY_RPID と ... の設定が必要です`）
- **無効のときは、`_RPID`・`_ORIGINS` を検証しない**（書き間違いがあっても起動する）。
  ただし `QUESTIONNAIRE_ADMIN_PASSKEY` の真偽値の書き間違い（`yes` など）は、有効にしたつもりで使えない事故を防ぐため止める
- 書き間違い（スキーム・ポート・パスつきの RP ID、`https` でない Origin、RP ID に従属しないホストの Origin）も起動時に止める。
  **`localhost`（と `*.localhost`）だけ `http` の Origin を許す**（開発用。ブラウザが安全なコンテキストとして扱うため）
- **Origin はスキーム・ホスト・ポートの完全一致。** 管理画面を複数のホスト名で開くなら、全部を並べる。
  RP ID は、それらのホスト名の共通の親（または同じ名前）にする
- **サブパス配置（`QUESTIONNAIRE_PATH_BASE`）でも RP ID・Origin はホスト名まで**。サブパスは含めない
- **`QUESTIONNAIRE_ADMIN_PASSKEY_RPID` を変えると、登録済みのパスキーはすべて使えなくなる**（5 章）

設定例（Azure App Service の「アプリケーション設定」、コンテナの環境変数、Kubernetes の ConfigMap のいずれでも同じ）:

```text
QUESTIONNAIRE_ADMIN_PASSKEY=true
QUESTIONNAIRE_ADMIN_PASSKEY_RPID=questionnaire.example.com
QUESTIONNAIRE_ADMIN_PASSKEY_ORIGINS=https://questionnaire.example.com
```

## 3. 有効にする手順

1. **管理画面を、HTTPS の固定のホスト名で開けることを確かめる。** パスキーは HTTPS（と `localhost`）でしか動かない。
   リバースプロキシの内側で `http` に落ちていても、**ブラウザが見る Origin** を設定する
2. **全員が、パスキー以外のログイン方法（パスワード・SAML・Pleasanter）で入れることを確かめる。**
   本アプリは、パスキーを消した結果ログイン方法が 1 つも無くなる削除を断るが、**判断できる範囲に限りがある**（6.1）
3. 上の 3 つの環境変数を設定してアプリを再起動する。**起動に失敗したら、ログの設定名を直す**
4. `GET /api/admin/session` の応答に `"passkeyEnabled": true` が出ること（未認証でも出る）、
   ログイン画面に「パスキー」のタブが出ること、マイアカウントにパスキーの管理が出ることを確かめる
5. 各管理者が、マイアカウントでパスキーを登録する（パスワードの再入力か、登録済みのパスキーでの確認が要る）。
   **実際の端末・認証器での登録とログインを、本番へ出す前に 1 回通す**（7 章。実機の確認は Core#217 と合わせる）

## 4. 監査

次の 5 つを、管理操作の記録（監査ログ。`Core_AuditLogs`）へ残す。名前は Core の決定のとおりで、**`POST /api/...` の形ではない**。

| 操作 | 失敗の理由 |
|---|---|
| `Passkey.Registered`（登録） | — |
| `Passkey.Removed`（削除。本人・管理者・DB の手作業） | — |
| `Passkey.Renamed`（名前の変更） | — |
| `Passkey.SignIn.Succeeded`（ログインの成功） | — |
| `Passkey.SignIn.Failed`（ログインの失敗） | 補足（`DetailJson`）の理由の印で区別する |

- **ログインの失敗は理由を区別して残す**: `unknown-credential`（未登録の認証器）・`challenge`（チャレンジの期限切れ・再利用）・
  `bad-signature`（署名の不一致）・`counter-regression`（署名カウンターの逆行。**複製の疑い。警告として見る**）・
  `origin`・`uv-missing`・`disabled`・`locked` ほか（一覧は Core の仕様書 3.10.8）
- **画面（応答）には、管理者の有無・認証器の未登録・署名の不一致を区別して出さない。** 区別はログにだけ残る
- **公開鍵・チャレンジ・署名は残さない。** 資格情報の ID は残す
- 管理操作の監査フィルタ（`AuditLogFilter`）はパスキーの経路に掛けていない（二重に残さないため）。
  記録できなくても操作は通し、`パスキーの監査イベントを監査ログへ残せなかった` とログに出す
- **失敗の記録の読み方**: 同じ IP から `unknown-credential`・`bad-signature` が続くなら総当たりを疑う。
  IP ごとのレート制限（次項）が先に止める

**レート制限。** パスキーのログイン（開始・完了）と、パスワードを受ける再認証の口は、パスワードのログインと**同じ枠**
（`admin-login`。`QUESTIONNAIRE_LOGIN_ATTEMPTS_PER_5MIN`、既定は 5 分で 10 回）を使う。
攻撃者が認証方式を使い分けても、試せる総数は増えない。**正規の利用者の試行が合算される**点は許容している（上限は既存のまま）。
上限に達すると 429。パスキーの失敗は、**アカウント側の失敗回数（締め出し）には数えない**
（資格情報の ID は秘密ではなく、数えると第三者が持ち主を締め出せるため）。パスワードでの再認証の失敗は、これまでどおり数える。

## 5. RP ID を変えるときの警告

**⚠️ `QUESTIONNAIRE_ADMIN_PASSKEY_RPID` を変える・公開のホスト名を変えると、登録済みのパスキーはすべて使えなくなる**
（パスキーは作ったときの RP ID に結び付く。サーバ側の行を直しても戻らない）。
手順と影響の詳細は、Core の手順書の 3 章に従う（事前に全員が別の方法で入れることを確かめ、利用者へ知らせ、変更後に登録し直させる）。

- 本アプリは RP ID を必ず明示するので、**「未設定のまま公開のホスト名を変えて、気付かずに使えなくなる」事故は起きない**
  （代わりに、変更を設定として意識して行う）
- **Origin だけを足す・変えるのは、RP ID が同じなら影響しない**
- 古い行は使えないまま一覧に残る。**各自が画面から削除し、新しく登録する**

## 6. 復旧と最終手段

### 6.1 本人の復旧と、本アプリの「使えるログイン方法」の判断

本人がパスキーを失くした・端末を替えたときは、**パスワード・SAML・Pleasanter のどれかで入って、登録し直す。**
復旧コードは発行しない。

「パスキー以外に入る方法があるか」（Core の P5）は、本アプリでは次のように判断する。

| 使える方法 | 数える条件 |
|---|---|
| パスワード | 合言葉のログインが塞がれておらず（`QUESTIONNAIRE_ADMIN_PASSWORD_SIGNIN`、または管理画面の「ログイン画面の方式」。SAML・Pleasanter のログインが両方無効な間は塞げない）、**招待を受け取り済み** |
| SAML | SAML が有効 |
| Pleasanter のログイン | Pleasanter のログインが有効 |

**⚠️ 限界: 「本人がパスワードを知っているか」は見分けられない。** SAML・Pleasanter の JIT で作られた管理者は、
誰も知らないパスワードを持つが、その印は表に無い。招待中でなければ「パスワードで入れる」と数えるので、
**SAML・Pleasanter のログインを無効にした環境では、JIT の管理者の最後のパスキーを消せてしまう**ことがある。
そのような構成にするときは、先に管理者へパスワードを決めさせる（招待の出し直し）。

### 6.2 管理者による削除（復旧）と DB の直接操作

- **管理者による削除**: `POST /api/admin/users/{管理者 ID}/passkeys/reset`（権限 `users.resetPasskeys`。
  `Administrator` と `UserAdministrator` が持つ。**2 要素の解除権限とは別**）。
  対象者の全パスキーを消し、**全セッションを失効**させる。自分は対象にできない（400）。
  **この操作の画面は別 Issue**。それまでは、管理 API を直接呼ぶ（ブラウザの開発者ツール、または cookie つきの `curl`）。
  本人確認を、電話・メールなど別の経路で確かめてから行うこと。**本人の代わりに登録することはできない**
- **DB の直接操作（最終手段）**: 管理画面に入れる管理者が 1 人も居ないときだけ。
  手順・SQL・確認は、Core の手順書の 5 章に従う（表は本アプリでも同じ `Core_AdminPasskeys`・`Core_AdminSessions`・`Core_AuditLogs`）。

> **⚠️ Core の手順書との差分: 監査ログの時刻の目盛り。** Core の手順書 5.7 は `OccurredAt` に **UTC** を入れる。
> **本アプリの `Core_AuditLogs.OccurredAt` は、サーバのローカル時刻の数字を持つ**（`AuditLogTime`。過去の行との目盛りを揃えるため）。
> 手で INSERT するときは、`SYSUTCDATETIME()`・`now() AT TIME ZONE 'UTC'`・`UTC_TIMESTAMP()`・`strftime(..., 'now')` ではなく、
> **サーバのローカル時刻**（`SYSDATETIME()`・`now()`・`NOW()`・`strftime(..., 'now', 'localtime')`。サーバの時間帯が違うなら、その時刻へ合わせる）を使う。
> 合わせないと、監査ログの画面の時刻が時間帯の差だけずれる。**この差分は実機で確かめていない**（コードの読みによる）。

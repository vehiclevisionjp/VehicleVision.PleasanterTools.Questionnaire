# 日本郵便参照元の確認-運用手順書

Issue #860（親 #804 手順 8）。[ルックアップ項目の仕様書](ルックアップ項目の仕様書.md) 13 章の未決事項 J1〜J9 を、
日本郵便への確認・規約確認・公式モック実測の作業として整理する。
**この文書は整理であり、確認の結果ではない。** 日本郵便への問い合わせ・登録・送信は人が行う（本文書の作成時には一切行っていない）。
仕様の決定（U1〜U11・12 章の方針）は変更しない。法的な判断はせず、規約の記載事実だけを整理する。
未確認の事項を確認済みとして扱わない。確認結果は、確認した人・日・出典を付けて 6 章の記録欄と仕様書 13 章へ追記する。
**2026-11-06 に Issue #912 で、日本郵便の公式モック（テスト環境）に対して J1・J6・J7・J9 の一部を実測した。
結果は 8 章に記す。公式モックでの実測であり、本番は未確認。**
**同日に Issue #923 で、ユーザーが「本番」と申告した接続情報を使い、日本郵便の本番のホストで J1・J6・J7・J9・J8 の一部を実測した。
結果は 9 章に記す。本番（ユーザー申告）での実測で、公式モックとは差があった。**
なお上の「作成時には一切行っていない」は #860 の作成時点の記述であり、実測は #912 で別に行った。

## 3. 確認できなかったこと（推測で埋めない）

- 検索へのトークンの渡し方（J1）。公式モックと本番（ユーザー申告。9.2）で `Authorization: Bearer` が通った。日本郵便の回答（Q1）は未取得。
- `expires_in` の更新余裕（J7）。単位は秒、期限切れは 401（本番。9.4）。更新余裕の推奨・同時更新は未確認。
- 本番の `count`・不存在・K+1（J6）は 9.3 で実測した。ページ終端の先は、公式モックの 200 空配列と異なり、本番では 404。
- 発行上限・多重発行・レートリミットの数値（J4）。規約は制限の存在だけを述べる。
- 外向き IP の指定方法、登録 IP との照合の有無、`User-Agent` の書式、固定 IP の要否（J8）。
  本番では、固定 IP 欄が空のまま、この環境の外向き IP を `x-forwarded-for` に入れたトークン取得が成功した（9.5）。
  それ以上（別の IP の拒否・照合の有無）は確認していない。
  第三者の解説記事に「固定 IP を登録する」とあるが、公式ページでは確認できていないため採用しない。
- 応答サイズの有限上限（J9）。本番の 11 件までの応答サイズと所要時間は 9.6。1000 件の応答は未測定。
- 規約全文の正確な条文・適用範囲。本製品（利用者が自組織で導入する形）が第三者提供の特約の対象になるか（J3）。**本書は判断しない。**
- 登録画面（ログイン後）の実際の手順・必要な権限・ver2.0 の API リファレンスとの版の対応（J2）。
- テスト用認証情報の画面の場所と記載内容（ログインが必要）。

## 5. 日本郵便への質問文の下書き

**送るのは人。** 送信前に、利用者（組織の担当者）が組織名・システム名・連絡先を実際の値に置き換える。
ID・シークレット・トークンの値は質問に書かない。回答は 6 章へ、受信日・回答者・窓口・原文へのリンクとともに記録する。
窓口は S5 の Web フォーム。

### 5.1 質問文（案）

> 件名: 郵便番号・デジタルアドレス API（検索・トークン）の仕様について
>
> 貴社の「郵便番号・デジタルアドレス API」の利用を検討している、〔組織名〕の〔氏名〕です。
> 〔システムの概要: Web アンケートの住所入力で、回答者が入力した 7 桁の郵便番号を検索 API に送り、住所を補完する〕。
> API リファレンス（本番・テスト）を読みましたが、記載がなかった次の点を教えてください。
> 〔利用する API の版: ver1.0 / ver2.0 のどちらか〕。

>
> Q2. 組織・システム登録の手順と、必要な権限（組織管理者・API 管理者等）、システム登録で入力する項目、テスト用認証情報の入手方法を教えてください。
>
> Q3. 〔利用者が自組織の環境に導入するソフトウェアに API を組み込み、そのソフトウェアの提供元が別の組織である場合〕の、利用規約・第三者提供の特約の適用の考え方と必要な手続きを教えてください。

>
> Q5. 検索応答の `count` は総件数ですか、そのページの件数ですか。

> 郵便番号に該当する住所が存在しない場合の応答（HTTP ステータスと本文）、7 桁未満（前方一致）の場合の `count` の意味を教えてください。

> Q7. トークン取得の `x-forwarded-for` に指定すべき値（サーバーの外向き IP か）、登録した IP との照合の有無、複数の外向き IP・NAT がある場合の扱い、`User-Agent` の書式の制約を教えてください。

  `searchtype` は 1 件の中ではなく最上位にある（郵便番号は `zipcode`）。
- 事業所個別郵便番号・デジタルアドレスの検索、`choikitype`・`searchtype` の指定は、本番では試していない。
- 日本郵便への回答（Q5）は未取得。

### 9.4 J7: `expires_in` と受入条件（本番）

- `expires_in` は 600（数値）。JWT の `exp - iat` も 600。**単位は秒**（本番）。
- トークンは**再取得のたびに別の値**（モックは毎回同一）。3 回取得して、3 つとも異なった。
- 再発行（2 回目）の後も、**旧トークン（1 回目）は期限までそのまま使えた**（検索 200）。旧トークンの失効は起きない。
- **期限（取得から 600 秒）を超えた旧トークンは 401**。`{"error_code":"401-1034-0002","message":"トークンが期限切れです"}`。
  期限切れを受け付けるモックと異なる。期限切れの検出は、`error_code` の末尾番号か `message` で区別できる可能性がある。
  ただし、番号の体系は 1 例しか観測しておらず、断定しない。
  モックのトークン不正は `トークンが不正です`（8.2）。
- 期限切れの後の再取得（3 回目）は成功し、その新しいトークンで検索できた。
- 期限の直前・直後の境界（何秒前まで通るか）、更新余裕の推奨、複数インスタンスの同時取得の上限・多重発行は、測っていない（未確認）。
  上の再発行の観測（旧トークンが生きる）から、多重発行そのものはエラーにならなかったが、上限は不明。

### 9.5 J8: 外向き IP・`x-forwarded-for`（本番）

- 固定 IP アドレスの欄が空の接続情報で、この環境の外向き IP を `x-forwarded-for` に入れたトークン取得が成功した。拒否（401・403・IP 制限のエラー）は 1 度も出ていない。
- 観測した事実はここまで。**IP の照合の有無は確認できていない**（この環境が許可されたのか、照合がそもそも無いのかは分からない）。
  別の IP を送る試験は、本番に偽の値を送らない方針のため実施していない。
- 検索側は `x-forwarded-for` なしで成功した。`User-Agent` は製品を識別する固定の文字列で受け付けられた。書式の制約は確認していない。
- 複数の外向き IP・NAT の扱い、登録 IP との照合の有無は、日本郵便への回答（Q7）が必要。

### 9.6 J9: 応答サイズと所要時間（本番）

| 応答 | バイト数 |
| --- | --- |
| 検索 1 件 | 約 600〜650 |
| 検索 11 件 | 約 6,350（1 件あたり約 580） |
| エラー（404・400・401） | 約 130〜170 |
| トークン取得の応答 | 約 440 |

- 1 件あたり約 600 バイトで、件数にほぼ比例した（11 件で約 6 KB）。K+1＝11 件の応答は十数 KB 以内に収まる。
  1000 件の応答は測っていない（外挿では約 600 KB だが、測定値ではない）。**応答サイズの有限上限は確認できなかった。**
- 検索の所要時間は、成功の応答で 86〜1,603 ms。最初の 1 回が 1.6 秒で、以降は 86〜550 ms の範囲（同じ 7 桁の 5 回反復は 86〜1,603 ms）。
  トークン取得は 210・561 ms、期限切れの 401 は 448 ms。
- 少数の試料の範囲の値で、**ばらつきがある（最大と最小で約 20 倍）**。タイムアウト（外部処理 5 秒）の設定値を決める統計には足りない。
  最初の 1 回（接続確立を含む）が遅い傾向は、モックと同様。

### 9.7 公式モックとの差（本番で異なった点）

| 項目 | 公式モック | 本番（ユーザー申告） |
| --- | --- | --- |
| トークン | 毎回同一。期限が過去の固定値でも検索が成功 | 毎回別。期限（600 秒）を過ぎると 401「トークンが期限切れです」。旧トークンは期限まで有効 |

| トークンの長さ | 約 600 文字 | 約 380 文字 |
| 同じもの | `Authorization: Bearer`・`expires_in` は秒（600）・`count` は総件数・不存在は 404・1 件のキー構造（28 個）・最上位の `searchtype`（文字列） | 同左 |

   専用の検証環境で実施し、本番の接続先・資格情報・個人情報を持ち込まない。
2. 対象 Pleasanter はリポジトリで固定した **1.5.8.1** を基準にする。
   実際のイメージタグ・ダイジェスト、画面で確認した版、参照ソースのコミットを記録する。

   **本アプリの DB 切替だけでは Pleasanter の DB は切り替わらない。**
   既存 compose の Pleasanter は SQL Server を使う。
4. 対象 Pleasanter 版の参照ソースで対応 DB と設定を確認し、

## 2. 架空の公開用マスターと専用アカウントを準備する

### 2.1 サイトと列

1. 検証専用の Pleasanter へ管理用アカウントでログインし、
   公開用の架空データだけを置く独立サイト「ルックアップ公開試験」を作る。
   実在の住所・顧客・社員情報を複製しない。
2. 列定義を取得して、次の用途の列を用意する。例の列名が実在することと、
   自由入力・選択設定・文字数・数値精度を確認して記録する。標準列数を仮定しない。
3. 公開用サイトとは別に「ルックアップ拒否試験」サイトを作り、同じキーの識別用レコードを置く。
   統合・継承の試験はさらに別の使い捨てサイトで行い、公開用マスターの前提を壊さない。

| 用途 | 列の例 | 準備する値・設定 |
| --- | --- | --- |
| キー 1 | 自由入力の `ClassA` | `00123`、`123`、`ABC-001`、`ABC-002`、`東京一`、`東京二`、内部空白つきの値 |
| キー 2 | 自由入力の `ClassE` | `office` と `home`。キー 1 が同じでもキー 2 が違う行を用意 |
| 返却テキスト | `ClassB` | 架空の地域名・空文字・最大長付近の値 |
| 返却選択値 | `ClassC` | 回答側 `Choice.Value` と一致する値、不一致値、空値 |
| 返却数値 | `NumA` | 0、範囲内、回答側の範囲外。生値と書式付き値を区別できる値 |
| 非許可列 | `DescriptionA` | `DO-NOT-RETURN` という架空の検出用文字列 |

キーの組み合わせを分けて、検索結果が 0 / 1 / 2 / 9 / 10 / 11 / 19 / 20 / 21 件になる集合を作る。
行ごとの識別子とキー・期待件数を試験台帳へ記録する。投入は準備用の管理アカウントで行い、
検索用アカウントには書き込みを許可しない。

特殊文字の照合確認用に `%`・`_`・`[`・`]`・引用符・予約値に似た文字列を持つ行も、
隔離した試験サイトに管理者が作る。これは製品のキー許可範囲を広げるためのデータではない。

### 2.2 専用アカウント

1. 検索専用の試験ユーザーを新規作成し、管理者・サイト管理・作成・更新・削除の権限を与えない。
   既定の組織・グループ経由の権限も調べ、対象サイト以外へ読める権限を持たせない。
2. 公開用マスターサイトだけに読み取りを付与する。
   画面での権限設定だけで済ませず、そのアカウントで公開用サイトを読めること、
   拒否サイトを読めないことを検索 API で確認する。
3. 専用 API キーを発行し、検証用クライアントのサーバー側だけで保管する。
   キーを URL・ブラウザ・コミット・共有ログ・画面の写しへ含めない。
   検証成果物は ApiKey と認証ヘッダーを除去してから保存する。
4. 読み取り専用の担保は使い捨てサイトで確認する。
   作成・更新・削除をそれぞれ要求し、拒否応答とデータ不変を準備用管理アカウントで照合する。
   意図せず成功した場合は不合格にして停止し、権限を修正する。
   これは権限検証専用の負の試験であり、製品の接続試験は読み取りだけとする。

## 3. 実装前に Pleasanter へ直接読み取り要求を送る

ルックアップ API は未実装なので、最初は検証用のサーバー側クライアントから
Pleasanter の `POST /api/items/{サイトID}/get` を直接呼ぶ。
[仕様書 5.2 節](ルックアップ項目の仕様書.md) の JSON を基準に、
専用キー・実在するサイト ID・列名を検証環境だけで差し替える。
`Offset=0`、既定 K=10 では `PageSize=11`、K=20 では `PageSize=21` を要求する。
API キーを除去した要求・応答、HTTP、取得行数、TotalCount、PageSize、Offset、
所要時間と応答バイト数を 6 章の記録へ残す。

### 3.1 検索・型・構文

| ID | 操作 | 合格条件・確認する事実 | 状態 |
| --- | --- | --- | --- |
| P01 | キー 1 だけ一致、キー 2 だけ一致、両方一致する行を置き、2 列の単一値条件を送る | 両方一致する行だけ。OR に広がらない | 未実施 |
| P02 | `ExactMatch` で `ABC` と `ABC-001`、`ForwardMatch` で `ABC` を照合 | 完全一致と前方一致の結果集合を記録。大文字小文字・全半角・日本語・空白の差も記録 | 未実施 |
| P03 | `00123` と `123`、0 を別の文字列キーとして送る | 先頭ゼロを失わず、0 を空値としない。列型ごとの一致結果を記録 | 未実施 |
| P04 | `GridColumns` を許可列だけにし、生値形式で取得 | 列名・生値・選択値・数値を確認。追加されるメタデータも列挙し、アプリ側で除去する対象を確定 | 未実施 |
| P05 | 0 / 1 / 2 件の集合と空の返却値を検索 | 件数と実配列が整合。空値の実際の表現（null・空文字・欠落）を記録 | 未実施 |
| P06 | 隔離サイトで `%`・`_`・`[`・`]`・引用符を単一値条件へ指定 | リテラル・構文・エラーのどれになるか、DB と列型ごとに記録。検索範囲の変化を検出 | 未実施 |
| P07 | 配列風・範囲式・`Own`・未設定等の予約値を指定 | 対象版のソースで予約値一覧を調べ、リテラルと解釈されない値・拒否すべき値を記録 | 未実施 |

P06・P07 は隔離された上流の挙動調査であり、製品から送信してよいという意味ではない。
JSON のエスケープと検索のリテラル照合を分けて確認する。
DB 別の照合順序・空白の比較・予約値を実測して、U6 の結果欄へ転記する。
安全な単一値条件を作れない列型・値は明示エラーとし、曖昧なまま対象へ加えない。

### 3.2 件数・上限・異常

| ID | 操作 | 合格条件・確認する事実 | 状態 |
| --- | --- | --- | --- |
| P08 | K=10 に対して 9 / 10 / 11 件、K=20 に対して 19 / 20 / 21 件を検索 | K+1 件を取得でき、総件数・配列・応答 PageSize が整合する | 未実施 |
| P09 | 隔離環境で上流の件数設定を変え、要求 PageSize の上下を比較 | 設定名・設定値・実効上限を記録。K+1 未満に切り詰められる条件を特定 | 未実施 |
| P10 | 専用キーの失効、権限除去、不明サイトを指定 | 401/403/404 等の実際の応答を記録。正常な 0 件と区別する | 未実施 |
| P11 | 隔離した中継先で 429/5xx、不正 JSON、欠落フィールド、総件数不整合を再現 | 上流の実応答と障害注入を区別して記録し、失敗を 0 件へ置換しない | 未実施 |
| P12 | 中継先の遅延を 5 秒前後に変え、接続切断と過大な応答も再現 | 経過時間・バイト数・中断位置を記録。自動再試行しない設計を確認 | 未実施 |

P09 の上流設定名や上限値は推測で埋めず、対象版の参照ソースと設定ファイル・実応答で確認する。
K+1 件に足りない設定は有効化を拒否する。最大 20 件を設定するなら 21 件の取得が必要。
上限を補う全件走査や無制限のページ巡回は行わない。
応答サイズの有限上限は P04・P08・P12 の実測値を根拠に設定し、採用値・余裕・理由を記録する。

| ID | 操作 | 合格条件 | 状態 |
| --- | --- | --- | --- |
| A01 | 専用アカウントで公開用サイトと拒否サイトの同一キーを検索 | 公開用だけを読める。拒否サイトの値・件数・列が漏れない | 未実施 |
| A02 | 公開用の許可列と非許可列、レコード個別の拒否を組み合わせる | 実効権限と射影を確認。公開可能な集合を超える結果を返さない | 未実施 |
| A03 | 使い捨てサイトでサイト統合を有効にし、統合先に同一キーの行を置く | 範囲拡大を検出し、初期の参照元として有効化を拒否できる | 未実施 |
| A04 | 親サイト・組織・グループの継承で別サイトを読める状態を作り、解除前後を比較 | 範囲拡大を検出し、該当構成の有効化を拒否できる | 未実施 |

サイト統合・継承で参照範囲が広がる構成は、読み取り自体が成功しても合格にしない。
この制約を、レート制限やキーの推測困難性で代替してはならない。

## 5. 実装後に本アプリ経由で再確認する

本節は実装前の上流試験と区別する。**現時点では全項目未実施。**
実装がないことを上流試験の合格で補わない。
4 RDBMS の保存・版固定をそれぞれ確認し、外部検索の接続先 DB も別に記録する。

1. アンケート管理者で定義・専用キー・接続試験を操作し、他の役割ではすべて拒否されることを確認する。
   同一ページの N=1〜5・M=1〜10、起点 1 ボタンを設定し、
   範囲超過・異ページ・重複・未対応型を保存時／公開前に拒否する。
   複製時にキーの再登録を求め、停止・失効が公開し直さず旧版にも効くことを確認する。
2. キーは 1 行テキスト・数値だけとし、数値も文字列で送る。先頭ゼロの保持を確認する。
   英数字・ハイフン・日本語・内部空白を受理し、前後空白を除去する。
   `%`・`_`・`[`・`]`・引用符・制御文字・予約構文は 400 で拒否し、外部呼び出しが 0 回であることを確認する。
   前方一致は既定無効、キー別許可時でも文字列列だけ・2 文字拒否／3 文字許可の境界を確認する。
3. 候補 0 / 1 / 2 / K / K+1 を確認する。K は既定 10 と上限 20 の両方を使う。
   上限超過・完結不明は 422 で候補なし、上流上限が K+1 未満なら設定の有効化を拒否する。
   許可列以外・内部 ID・総件数が回答 API に残らないことを確認する。
4. 既存入力があるときの確認と取消、不適合時の警告と部分反映、空値・非表示先の保持を確認する。
   複数選択・日付は初期対象外。反映後の通常検証・分岐・下書きと古い応答の破棄を確認する。
5. 本文 4095 / 4096 / 4097 バイト、外部検索 5 秒、フォーム同時実行 3 / 4 / 5 の境界を確認する。
   回答者 5 分 30 回・IP 5 分 60 回・フォーム 1 分 120 回を別々に超過させ、
   429 と Retry-After、超過後の外部呼び出し 0 回を確認する。
   署名トークンの改変・別フォーム流用・30 分期限切れも拒否する。
6. 複数インスタンスで枠を共有し、共有ストア停止時は拒否されることを確認する。
   成功扱い・0 件扱い・プロセス内退避をしないこと、外部異常が仕様書 4.3 節のコードになることを確認する。
7. 公開 API から下書きを取得できず、認証つきの別管理経路でのみプレビューできることを確認する。
   公開データの警告が必ず表示され、実測未完了の設定を有効化できないことを確認する。
8. 成功・失敗とも no-store とし、サーバー側の結果キャッシュがないこと、
   キー・候補・API キーがログ・トレース・永続キャッシュへ出ないことを確認する。
   検索中の参照元への書き込みが 0 回であることも確認する。

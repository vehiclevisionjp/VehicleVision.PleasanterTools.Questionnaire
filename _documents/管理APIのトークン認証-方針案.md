# 管理 API のトークン認証 方針案

管理 API（`/api/admin/**`）を、ブラウザのセッションを使わずに、スクリプトや自動操作から使えるようにする設計案
（Issue #1012。親 #1005）。

> **本書は設計案であり、実装はまだ無い。** 認証・権限に関わるため、案の承認（レビュー）を得てから
> 実装の Issue を起こす。本書の `【要確認】` は、確認できていない点・決めていない点。
> 現状の確認日は 2026-11-18、確認したコミットは `471416bec39ce62a7f10b5d423f126b1984c16bb`（`develop`）。
> Pleasanter 本体の挙動には依存しないので、`_reference/` は読んでいない。

## 1. 背景と範囲

現在の `/api/admin/**` は、**ログイン ID ＋ パスワード ＋ 2 要素 ＋ CSRF 対策**を通ったブラウザのセッションが前提で、
スクリプトからは使えない（`POST /api/admin/login` → `.../login/totp` の 2 段階で、
cookie `q.admin` を得る。[`非機能設計.md`](非機能設計.md) 1 章「管理画面」）。

| | 内容 |
| --- | --- |
| 対象（初版） | アンケート定義の取得・更新・公開、書き出し・取り込み（#1009） |
| 対象外（初版） | 管理者・ユーザー・2 要素・設定・SAML・SSO・メンテナンス・ルックアップ・完全削除・操作の記録の閲覧 |
| 対象外 | 回答画面の API（`/api/forms/**`。cookie 認証を使わず、本件と無関係） |
| 対象外 | Pleasanter の API キー。**別物であり、ブラウザへ渡さない規約（必須規約 8）にも触れない** |

> **Issue 本文との食い違い。** Issue #1012 の本文は書き出し・取り込みを `#1008` と書いているが、
> `#1008` は「テスト公開への反映が失敗しても、テスト公開が外れないようにする」で別件。
> 書き出し・取り込みは **#1009**（「フォーム定義の書き出し・取り込み（JSON）を足す」）として扱う。

## 2. 現状（実物の確認）

| 項目 | 現状 | 根拠 |
| --- | --- | --- |
| 認証スキーム | cookie だけ（`Admin.Session`・`Pending`・`Reenroll`）。Bearer など他の方式は無い | `Web/Program.cs:550-565` |
| 認可 | 権限ごとのポリシー（`AdminPermissions.PolicyOf`）。**全ポリシーが Session スキームだけを見る**。役割の claim からその都度対応表を引く | `Web/Program.cs:572-597` |
| アンケート系の群 | `/api/admin/surveys` に `surveys.read` を群で掛け、書き込み・公開は口ごとに足す。**書き込み系だけ**を `AuditLogFilter` が記録する | `Web/Endpoints/AdminSurveyEndpoints.cs:49-54` |
| CSRF | `/api/admin/**` の `GET`・`HEAD`・`OPTIONS`・`TRACE` 以外で `Sec-Fetch-Site` → `Origin` を検証し、**どちらも無い要求は通す**。例外は SAML の `acs`・`slo` のみ | `Web/Services/AdminCsrfGuard.cs`、[`管理画面のCSRF対策-運用手順書.md`](管理画面のCSRF対策-運用手順書.md) 2 章 |
| ミドルウェアの順 | CSRF → **レート制限** → 認証 → 認可。**レート制限は認証の前** | `Web/Program.cs:1012-1017` |
| レート制限 | 送信元 IP が軸。ログイン試行は別枠（IP ごと 5 分に 10 回）。回答画面以外は **`PublicId` の軸に巻き込まない**（#311） | `Web/Program.cs:674-770`、`非機能設計.md` 1 章「レート制限」 |
| 招待トークン | 256 ビット乱数・**ハッシュのみ保存**・PBKDF2 は使わない（ハッシュで引けるように） | `非機能設計.md` 1 章「管理者の管理」 |
| セッションの保存 | cookie の ID は 256 bit で、ストアには SHA-256 だけを置く | `非機能設計.md` 1 章「実装」 |

⚠️ **全ポリシーが Session スキームだけを見る点が重要。** トークンの認証スキームを足しても、
既存のポリシーは通らない。逆に、**群のポリシーへ Bearer を足すと、その群のすべての口がトークンで開く**
（例: 群に `surveys.read` を掛けている `AdminSurveyEndpoints` では、公開・停止・アーカイブ・完全削除の口まで）。
したがって、**トークンを許す口は 1 つずつ明示する**（3.2 章）。

## 3. 論点と選択肢

### 3.1 トークンの形式と持ち主

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **A（推奨）** | **不透明なトークン（256 bit 乱数）を DB にハッシュで保存。** 管理者ユーザーに紐づく個人トークン | 失効・停止・役割変更が**その場で効く**。既存の招待トークン・セッション ID と同じ流儀で実装が小さい | 要求のたびに DB を引く（既存のセッション検証も同じ） |
| B | JWT（署名付きの自己完結トークン） | DB を引かずに検証できる | **失効がその場で効かない**（止めた管理者を即時に追い出す既存の方針に反する）。鍵の管理・ローテーションが増える |
| C | OAuth 2.0 の client credentials・mTLS | 標準的。クライアントごとの管理 | 認可サーバが要る。本アプリは IdP を持たない（Pleasanter も IdP ではない）。範囲に対して過大 |
| D | セッション cookie をスクリプトで使い回す | 実装が要らない | **2 要素をスクリプトで通せない**。期限が 8 時間。個人の資格情報の持ち出しになる |

**推奨は A。** 持ち主は**発行した管理者本人**とする（サービスアカウント専用の種別は初版では作らない）。

- 形式は `qat_` ＋ 識別用の短い公開部 ＋ 乱数部。**固定プレフィックス**により、漏えい検知（GitHub の秘密スキャン、
  社内の DLP）で見つけやすくする
- 保存は **SHA-256 のハッシュのみ**。**PBKDF2 は使わない**（256 ビットの乱数に辞書攻撃は成立せず、
  PBKDF2 では全件照合になり、認証前の入口を重い計算に晒す。招待トークンと同じ判断）
- 照合は**ハッシュで引いたうえで定数時間比較**する
- 発行時の画面に**平文を 1 回だけ表示する**。再表示はできない（忘れたら失効して再発行）
- 持ち主が**止められた・削除された**ら、そのトークンは使えない（トークン側の状態を更新せずに、
  要求のたびに持ち主の状態を見る。`AdminSessionGuard` と同じ流儀）

### 3.2 スコープ（権限の絞り込みと、トークンを許す口）

**新しい権限を増やさず、既存の権限のサブセットをスコープとする。** 実効の権限は
**「持ち主の現在の役割の権限」∩「トークンに付けたスコープ」**とする。

- 役割を降格すると、トークンも**その場で**弱くなる（権限は cookie と同じくトークンへ焼かない）
- **トークンに付けられるスコープは許可リスト（初版）に限る。**

| 権限 | トークンに付けられるか | 備考 |
| --- | --- | --- |
| `surveys.read` | **可** | アンケート定義・版の取得 |
| `surveys.write` | **可** | 定義の更新 |
| `surveys.publish` | **可** | 公開・停止など。**付けるのは最も慎重に**（誤公開の影響が大きい） |
| 書き出し・取り込み（#1009） | **可（権限名は未定）** | 【要確認】`surveys.read` / `surveys.write` を流用するか、`surveys.export` / `surveys.import` を足すか。取り込みは定義を書き換えるので、少なくとも `surveys.write` 相当 |
| `surveys.delete` | **不可** | 完全削除は `Administrator` の画面操作に限る |
| `lookups.manage` | **不可** | ルックアップ専用の API キーを扱う |
| `users.*`・`users.resetTwoFactor` | **不可** | 乗っ取りの足場になる。トークンで人・2 要素を触らせない |
| `settings.*`・`maintenance.manage` | **不可** | SAML・SSO・アプリ設定・メンテナンス |
| `audit.read`・`outbox.*`・`notifications.read`・`templates.*` | **不可（初版）** | 範囲外。必要になったら別 Issue |
| **トークンの発行・失効そのもの** | **不可** | **トークンでトークンを作らせない**（足場の増殖を防ぐ） |

**トークンを許す口の決め方。**

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **A（推奨）** | **口ごとに許可を宣言する（既定は拒否）。** 例: `AllowApiToken(scope)` を付けた口だけ、トークン用の認証スキームを通す | 口が増えても、足し忘れは「使えない」側に倒れる。レビューで一覧できる |
| B | 群のポリシーへ Bearer を足す | **群の全口が開く**（2 章）。完全削除や 2 要素の口まで巻き込む |
| C | 別の経路（`/api/automation/**` など）に口を作り直す | 境界は明快だが、画面と二重実装になる |

**推奨は A。** 初版で許す口は、アンケートの取得・版・更新・公開・停止・再開・書き出し・取り込みに絞る。
【要確認】`AdminSurveyEndpoints` の個々の口のうち、どれを初版に含めるか（2 章の一覧から確定する）。

**アンケート単位の絞り込み**（特定のアンケートだけに限るトークン）は、初版では**作らない**。
【要確認】CI で 1 つのアンケートだけを更新する用途が主か。そうなら後の拡張として価値が高い。

### 3.3 発行・保管

- **発行できるのは、`Admin.Session`（2 要素まで通った状態）のブラウザだけ。** 途中状態（`Pending`）・トークン自身では不可
- **発行時にパスワードを再確認する。** 2 要素の登録し直しと同じ理由（離席中の画面を奪われただけで、
  永続的な資格情報を作らせない）。失敗は**ログインと同じ道で数え、締め出す**（ここだけ免れると総当たりの抜け道）
- 発行できる人は、`surveys.*` を持つ役割（`Administrator`・`SurveyAdministrator`・`Editor` のうち、付けるスコープが自分の権限に収まる人）。
  **自分の権限を超えるスコープは付けられない**
- 管理画面に**自分のトークンの一覧**（名前・公開部・スコープ・作成日・期限・最終使用日時・最終使用 IP）を出す。**値は出さない**
- 発行・一覧・失効の口は**ブラウザのセッションだけ**で、`AdminCsrfGuard` の対象のまま
- **機能は既定で無効にする**（SAML・Pleasanter SSO と同じ）。`QUESTIONNAIRE_ADMIN_API_TOKENS`（仮称。
  `disabled`（既定）/ `enabled`）。**知らない値は起動時に落とす**（黙って既定へ落ちると、有効にしたつもりで無効のまま動く）
- 保管先: 本アプリの DB。表の置き場所は【要確認】。管理者・セッション・操作の記録が Core.Data の `Core_*` にあるので、
  共有部品へ置くか（共有物は Core に置く方針）、本アプリの `Data` に置くか。Core に置くと、Core のリリースを先に挟む
- **平文を DB・ログ・例外・キャッシュに残さない。** 資格情報の規約（[`非機能設計.md`](非機能設計.md) 1 章「資格情報」）と同じ
- **TLS 必須。** HTTPS でない要求に載ったトークンは、**使えないものとして扱う**。
  【要確認】本アプリは `CookieSecurePolicy.SameAsRequest` で HTTP を許容している。トークンは検証環境の `http://localhost` を除いて拒むか

### 3.4 期限と失効

- **期限は必須。** 既定 90 日、上限 365 日、**無期限は作れない**。期限は設定で変えられる
- 更新（ローテーション）は**再発行**で行う。旧トークンは、利用者が手動で失効するまで有効（切り替えの猶予のため）。
  期限の通知は初版では作らない。【要確認】一覧に残り日数を出すだけで足りるか
- **失効の口**は、本人と `users.write` を持つ人（他人のトークン。操作を記録する）。**失効はその場で効く**
- **自動で失効させる条件**: 持ち主の**停止・削除**。役割の降格は失効させず、実効権限が縮む（3.2 章）。
  【要確認】**パスワード変更・2 要素の解除**でトークンを失効させるか。cookie は他端末を失効させる。
  トークンはパスワードと独立した資格情報なので、既定では失効させず、手動の一括失効を用意する案が妥当
- **最終使用日時の更新は間引く**（例: 1 分に 1 回まで）。要求のたびに書くと、読み取りの多いスクリプトで書き込みが増える
- **長期間使われていないトークンを一覧で分かるようにする**（棚卸し。[`管理者の棚卸し-運用手順書.md`](管理者の棚卸し-運用手順書.md) に節を足す）。
  自動で無効にはしない（管理者の棚卸しと同じ判断）

### 3.5 CSRF との関係

**結論: トークン認証のために CSRF の除外（`CrossSitePostPaths` への追加）は要らない。除外を足さないこと。**

CSRF は、ブラウザが**要求へ自動で付ける資格情報**（cookie など）を、別オリジンのページに悪用される攻撃である。

- **`Authorization` ヘッダのトークンは、ブラウザが自動で付けない。** 攻撃ページがトークンを知らない限り、
  別オリジンのページから送る要求には付かない。cookie と違い、**ambient authority が無い**
- **現行のガードはすでにこの形で通す。** ブラウザ以外（curl・CI）の要求は `Sec-Fetch-Site` も `Origin` も付けないので、
  ガードの規則 3 で通る（[`管理画面のCSRF対策-運用手順書.md`](管理画面のCSRF対策-運用手順書.md) 2 章）。**ガードの変更は不要**
- 逆に、**ブラウザから `Origin` 付きで Bearer を送る要求は、今のガードで拒まれる**（同一オリジンの画面以外は 403）。
  CORS も有効にしない。**トークンはブラウザ上のスクリプトで使わせない**（トークンをブラウザへ置かせない）

⚠️ **守るべき条件。** これが成り立つのは「トークンの要求が cookie を使わない」ときだけ。

1. **`Authorization: Bearer` がある要求は、トークンだけで認証する。cookie（`q.admin`）は評価しない。**
   両方を許すと、cookie を足場にした CSRF がトークン経路で成立し得る／トークンの権限で cookie の検証を回避し得る
2. **トークンを URL・クエリ・本文で受け取らない。** `Authorization` ヘッダだけ（URL はアクセスログ・Referer に残る）
3. 認証スキームの選択は、**ヘッダの有無で決める**（`ForwardDefaultSelector` など）。
   ポリシーに Session と Bearer の両方を並べて「どれかが通れば可」にしない
4. トークンの要求が**拒まれた場合に、cookie へフォールバックしない**

【要確認】Pleasanter と同一ホストのサブパス配置（[`サブパス配置-運用手順書.md`](サブパス配置-運用手順書.md)）で、
`Authorization` ヘッダがリバースプロキシ（IIS・Apache・Nginx・Azure）で落ちないか。実機未検証。

### 3.6 レート制限とブルートフォース対策

- 現状、**レート制限は認証の前に走る**（`Web/Program.cs:1014` が認証 `:1016` の前）。このため、
  トークン単位の枠は**認証前には持ち主を知らない**。**ヘッダ値のハッシュを区画のキーにする**案はあるが、
  偽トークンを大量に送られると区画が増える。**先に送信元 IP の枠で絞る**（IP の枠 → トークンの枠の順）
- 軸（推奨）

| 軸 | 目的 | 備考 |
| --- | --- | --- |
| 送信元 IP（トークン認証の失敗だけを数える） | 推測・DB への負荷 | ログインと同じく**別枠**。通常の API の枠に紛れさせない |
| トークン（識別後） | 1 本のトークンの暴走（スクリプトの無限ループ） | 書き込み系は読み取りより低く |
| 送信元 IP × 書き出し・取り込み | **1 回が重い操作**（定義の一括取り込み）を通常 API と同じ枠で数えない | #311 と同じ考え方 |
| **`PublicId` の軸には巻き込まない** | 回答者の枠を管理者の操作が食わない | #311 の教訓 |

- 超過は `429` と `Retry-After`。**DB へ書く前に効かせる**。制限値は設定で外部化する
- **トークン単位で恒久的に締め出さない。** 推測ではなく、持ち主へ嫌がらせの停止をされる経路になる。
  256 ビットの乱数は**総当たりが現実的でない**ので、守る対象は「当てられること」ではなく「負荷」と「漏えい後の悪用の検知」
- **失敗の応答を区別しない。** 不存在・期限切れ・失効・持ち主の停止は**同じ `401`**（理由は返さず、監査へ）。
  一方、**スコープ不足は `403`**（トークンの存在が確定しているので、区別しても情報は増えない）
- **失敗の記録にトークンの値を残さない。** 公開部（プレフィックス）だけを残す
- 失敗が連続した IP は監査から追えること。【要確認】メトリクス・アラートの出し先（既存の監視 API があるか）

### 3.7 操作の記録（監査）

現状の `AuditLogFilter` は**書き込み系だけ**を記録し、読み取りは残さない（Issue #19）。トークンでは次を足す。

- **記録する**: 発行・失効（自動の失効を含む）・期限切れの検知・認証の失敗（公開部と送信元 IP）・
  スコープ不足（403）・**トークンでの書き込み**（既存どおり）
- **トークンでの書き出し（#1009）は記録する。** 読み取りだが、**定義の一括持ち出し**なので漏えい時の追跡に必要。
  通常の読み取り（一覧・詳細）は残さない（既存どおり）
- **操作の主体にトークンを残す**: 「誰が」に、持ち主のログイン ID と**トークンの識別（名前・公開部）**を書く。
  人が画面で行った操作と、スクリプトの操作を後から分けられるようにする
- **値を残さない**: トークン本体・書き出した定義の本文・`Authorization` ヘッダを記録しない
- 【要確認】`Core_AuditLogs` の列に、主体の種別（人／トークン）を持てるか。無ければ補足（`Detail` の JSON）へ入れる案で足りるか。
  Core.Data の定義を確認する
- 保持期間は既存の監査と同じ（[`非機能設計.md`](非機能設計.md) 5 章）

### 3.8 漏えい時の運用

トークンが漏れたら、**第三者がその持ち主の権限（の部分集合）でアンケートを読み書きできる**。
**2 要素を迂回する**資格情報である点が、cookie との本質的な違い。

| 段階 | 手順 |
| --- | --- |
| 1. 止める | 持ち主または `users.write` を持つ人が、該当トークンを失効する。**その場で効く**。持ち主のアカウントごと止める手もある（トークンが全部止まる） |
| 2. 範囲を確かめる | 監査で、そのトークン（公開部）の使用を確認する。最終使用日時・最終使用 IP も見る |
| 3. 影響を戻す | **アンケートの版の履歴**（`GET /api/admin/surveys/{id}/versions`）で、改ざん・誤公開を確かめて戻す。公開中のアンケートが書き換わっていないかを優先して見る |
| 4. 再発行 | 新しいトークンを作り、漏えい元（CI のログ・設定・リポジトリ）を直す |
| 5. 一括失効 | 全トークンを一度に失効する手段を `Administrator` に用意する（機能を `disabled` にして再起動する方法が、実装なしの最後の手段） |

- 固定プレフィックスにより、**リポジトリ・ログへの混入を検知しやすく**する
- 運用手順書（別 PR）: 保管（CI のシークレット機能）・最小スコープ・短い期限・ローテーション・漏えい時の連絡先
- 【要確認】コミットされたトークンを GitHub の秘密スキャンに登録するか（パートナー登録の要否）。当面は社内の運用のみ

### 3.9 既存の管理者権限との対応

| 役割 | トークンの発行 | 付けられるスコープ（初版） |
| --- | --- | --- |
| `Administrator` | 可 | `surveys.read` `surveys.write` `surveys.publish`（書き出し・取り込み）。**`Administrator` の他の権限はトークンに載せない** |
| `SurveyAdministrator` | 可 | 同上（役割が持つ範囲内） |
| `Editor` | 可 | `surveys.read` `surveys.write`（**`surveys.publish` を持たないので公開は付けられない**） |
| `UserAdministrator` | **不可** | `surveys.*` を持たない |
| `Auditor` | **不可** | 見るだけの役割。初版の範囲外 |

- 実効の権限 ＝ 持ち主の役割の権限 ∩ スコープ。**役割より強いトークンは作れない**
- **知らない役割には何も持たせない**（既存の方針どおり）
- SAML・Pleasanter SSO で入った管理者も、同じ表に従う。JIT で作った人はパスワードを持たないので、
  **パスワードの再確認（3.3 章）が使えない**。【要確認】その場合は発行を `Administrator` に任せるか、2 要素の再確認で代替するか

## 4. 推奨案のまとめ

| 論点 | 推奨 |
| --- | --- |
| 形式・持ち主 | 不透明な 256 bit トークン・SHA-256 のハッシュだけ保存・発行した管理者に紐づく個人トークン・表示は 1 回だけ |
| スコープ | 既存権限のサブセットを許可リストで限る。実効 ＝ 役割 ∩ スコープ。トークンを許す口は**口ごとに明示**（既定は拒否） |
| 発行 | `Admin.Session` ＋パスワード再確認のみ。トークンでトークンは作れない。機能は既定で無効 |
| 期限・失効 | 期限必須（既定 90 日・上限 365 日）。失効はその場で効く。持ち主の停止・削除で自動失効 |
| CSRF | **除外は足さない。** ガードは現状のまま。トークンの要求は cookie を評価せず、`Authorization` ヘッダだけで認証する |
| レート制限 | IP の枠（失敗の別枠）→ トークンの枠。重い操作は別枠。恒久の締め出しはしない。失敗は `401` に統一 |
| 監査 | 発行・失効・失敗・書き込み・**書き出し**を、トークンの識別つきで記録。値は残さない |
| 漏えい時 | 失効 → 監査で範囲確認 → 版の履歴で戻す → 再発行。固定プレフィックスで検知 |

## 6. 要確認の一覧

1. 書き出し・取り込み（#1009）の権限名（流用か新設か）
2. 初版でトークンを許す口の確定（`AdminSurveyEndpoints` の口の洗い出し）
3. アンケート単位のスコープ絞り込みを初版で要るか
4. トークンの表の置き場所（Core.Data か、本アプリの `Data` か）
5. HTTP（非 TLS）の扱い。検証環境の例外
6. パスワード変更・2 要素の解除でトークンを失効させるか
7. `Core_AuditLogs` に主体の種別（人／トークン）を持てるか
8. SAML・SSO の JIT の管理者（パスワード無し）の発行手段
9. リバースプロキシが `Authorization` ヘッダを通すか（実機未検証）
10. 秘密スキャンへの登録・異常のアラートの出し先
11. 期限・IP の既定値（90 日・365 日・枠の回数）の妥当性
12. 任意の IP 許可リスト（トークンごとに接続元を限る）を初版に入れるか。2 要素を迂回する資格情報なので、有効な緩和策になる

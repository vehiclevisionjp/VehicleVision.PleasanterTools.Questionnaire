## 1. 標準の列は型ごとに 26 本（A〜Z）

`Results` / `Issues` の実列を数えた結果。

| 型 | 本数 | 範囲 |
| --- | --- | --- |
| Class | **126** | `ClassA`〜`ClassZ`（26）＋ `Class001`〜`Class100`（100） |
| Num | 26 | `NumA`〜`NumZ` |
| Date | 26 | `DateA`〜`DateZ` |
| Description | 26 | `DescriptionA`〜`DescriptionZ` |
| Check | 26 | `CheckA`〜`CheckZ` |
| Attachments | 26 | `AttachmentsA`〜`AttachmentsZ` |

**`Class` だけ 126 なのは、CodeDefiner の `trial` が項目拡張を既定設定で有効化し
`Class001`〜`Class100` を追加したため。** 素の標準は **どの型も 26 本**。
項目拡張の本数は定義ファイルで変えられる（`Implem.ParameterAccessor/Parts/ExtendedColumns.cs`）。

### 列の型と桁（`Results`）

| 列 | 型 | 桁 |
| --- | --- | --- |
| `ClassA` | `nvarchar` | 2048 バイト＝**1024 文字** |
| `NumA` | `decimal` | precision 19 / scale 4 |
| `DateA` | `datetime` | **`datetime2` ではない**（1753 年以降・約 3.33ms 精度） |
| `DescriptionA` | `nvarchar(max)` | 事実上無制限 |
| `CheckA` | `bit` | |
| `AttachmentsA` | `nvarchar(max)` | |

**設計への影響。** 選択肢や短答を `Class` へ写すときは **1024 文字**が上限。
複数選択を連結して 1 列へ入れる方式は、選択肢が多いと溢れる。

## 2. `GetSite` の応答に `ChoiceHash` は載らない

**確認結果：載らない。** `ChoicesText`（生の選択肢定義）は載る。

`Column.ChoiceHash` に `[NonSerialized]` が付いているとおりの挙動だった。

**設計への影響。** 選択肢は **`ChoicesText` を自前で解析する**必要がある。
他サイトへのリンクや部署・ユーザ参照といった動的な指定の解決も自前になる。

## 3. `Upsert` は `Keys` で既存レコードへ集約される

**確認結果：期待どおり動く。**

> **ただし本設計では使わないことにした**（2026-08-18）。`Keys` に使う列で
> Pleasanter の列を 1 本消費するため。回答の突き止めは `ReferenceId` と
> 本アプリ側の対応表で行う（[`アーキテクチャ方針.md`](アーキテクチャ方針.md) 9 章）。
> **`Upsert` が使えること自体は事実として残す。** 方針が変わったときに再確認しないで済む。

```text
1 回目 Upsert(Keys=["ClassA"], ClassA=<GUID>) → Id 2 / "has been created"
2 回目 Upsert(Keys=["ClassA"], ClassA=<GUID>) → Id 2 / "has been updated"
Get → 件数 1
```

**同じ GUID で何度送っても 1 件のまま。** 再送が冪等であることを実機で確認した。

## 4. 日時は「サーバの OS ローカル時刻」で保存され、「API キー保有ユーザの TimeZone」で返る

**最も事故りやすい挙動。実測で確定した。**

| 操作 | 値 |
| --- | --- |
| API へ送った値（ユーザ TimeZone = `UTC`） | `2026-03-01T09:00:00` |
| **DB に保存された値** | **`2026-03-01T18:00:00`**（＋9 時間） |
| API から返った値（ユーザ TimeZone = `UTC`） | `2026-03-01T09:00:00` |
| **同じレコードを ユーザ TimeZone = `Tokyo Standard Time` で読んだ値** | **`2026-03-01T18:00:00`** |

`CreatedTime` でも同じ差が出た（DB `2026-08-18T17:07:23` / API `2026-08-18T08:07:23Z`）。

### 分かったこと

1. **DB には Pleasanter サーバの OS ローカル時刻で書かれる**（このコンテナは `Asia/Tokyo`）
2. **API の境界で、APIキー保有ユーザの `TimeZone` との間で変換される**
3. **APIキー保有ユーザの `TimeZone` を変えると、保存済みレコードの見え方が変わる。**
   データは 1 バイトも変わっていないのに、同じ行が 09:00 にも 18:00 にも見える

### 設計への影響（重要）

- **APIキー保有ユーザの `TimeZone` は、本アプリの設定として固定し、運用中に変更しない。**
  変えた瞬間に過去の回答日時の解釈がずれる
- **Pleasanter サーバの OS タイムゾーンも運用中に変更しない。**
  変えると、以後の保存値の基準だけが変わり、過去分と混ざる
- 本アプリ側は `DateTimeOffset` で扱い、**API へ渡す直前にだけ、APIキー保有ユーザの
  `TimeZone` 基準の値へ変換する**

## 5. 未設定の日付は `1899-12-30T00:00:00` で返る

日付列に値を入れずにレコードを作ると、`DateHash` に `1899-12-30T00:00:00` が入って返った。

**設計への影響。** **「未回答」と「1899-12-30 と回答」を API 応答だけでは区別できない。**
任意回答の日付設問では、未回答を別の列（`CheckA` 等）で表すか、
この値を未回答とみなす規約を決める必要がある。
**送る側の扱いは 9 章で決着した**（`DateTime.MinValue` を送る）。

## 6. 添付ファイルは `Upsert` に Base64 で同梱できる

**確認結果：同梱できる。** 専用の先行アップロードは不要だった。

```json
{ "AttachmentsHash": { "AttachmentsA": [
  { "Name": "a.txt", "Base64": "aGVsbG8...", "Added": true, "ContentType": "text/plain" } ] } }
```

- `Get` で返るのは **`Guid` / `Name` / `Size` のみ**。内容は含まれない
  （内容は `api/binaries/{guid}/get` 系で取る）
- **フィールド名は `Name` ＋ `Base64` ＋ `Added`。**
  `FileName` ＋ `Base64Binary` で送ったら `400 Invalid json data` になった
- **対象の列がサイト設定に無いと、エラーにならず静かに無視される**
  （最初に踏んだ。レコードは作成されるが `AttachmentsHash` が空で返る）

**設計への影響。** 送信待ちの `PayloadJson` に Base64 が載るため、
添付のサイズ上限を決めて超えるものは受け付けないこと。

## 7. `Description` 列は部分一致で検索できる

**確認結果：`View.ColumnFilterHash` に `Description` 系の列を指定すると、部分一致で引ける。**

```json
{ "View": { "ColumnFilterHash": { "DescriptionA": "tok-7f3a9c2e5b184d60" } } }
```

| 指定 | 結果 |
| --- | --- |
| 既定（何も指定しない） | **部分一致。** 該当する 1 件だけ返った（別レコードは引っかからない） |
| `ColumnFilterSearchTypes` に `ExactMatch` | **0 件。** 列の値全体は JSON なので、トークンとは一致しない |

**設計への影響（重要）。**

**応答が返らなかった `Create` を照合できる。** 回答の正本 JSON に回答トークンを埋めておけば、
`Get` で部分一致検索して「レコードができたかどうか」を確かめられる
（[`アーキテクチャ方針.md`](アーキテクチャ方針.md) 10 章）。
**Pleasanter の列を追加で消費しない。**

> **部分一致は `LIKE '%…%'` になるため索引が効かない。**
> 照合は応答不明のときだけ走る例外処理なので許容するが、**通常の読み出しには使わないこと。**

## 8. 添付を消すには `Guid` ＋ `Deleted` を送る

**空配列を送っても消えない。** `AttachmentsHash` に `[]` を入れて `Update` しても、
既にある添付はそのまま残る（2026-08-18 / Pleasanter 1.5.7.0）。

```json
{ "AttachmentsHash": { "AttachmentsA": [] } }
```

**消すときは `Guid` と `Deleted` を送る。**

```json
{ "AttachmentsHash": { "AttachmentsA": [ { "Guid": "9B631957...", "Deleted": true } ] } }
```

- `Added: true` は「足す」の指定であって、「これが全部」という意味ではない
- **削除時の `Guid` は必ず大文字**（マニュアルの明記。実際に `Get` は大文字で返す）
- **`Guid` は `Get` でしか得られない。** つまり消すには**送信前に読み直す往復が要る**
- マニュアルの例は `"Deleted": 1`。`true` でも通ることを実機で確認した
- 同じ配列に「消す」と「足す」を混ぜられる（差し替えが 1 回で済む）

出典（いずれも 2026-08-18 参照）。

- <https://pleasanter.org/manual/api-record-update>
- `_reference/Implem.Pleasanter/Implem.Pleasanter/Libraries/DataTypes/Attachment.cs`
  （`Guid` / `Deleted` / `Added` / `Base64` のフィールド定義）

**設計への影響。** 送り直しは「足す」ではなく「置き換える」として扱う。
**添付の割り当てがあり、かつ既にレコードがあるときだけ**読み直すことで、
添付を使わないアンケートに往復を増やさない。

## 9. 未回答の日付は `DateTime.MinValue` を送って消す

**検証日 2026-08-20。** Issue #84 の決着のために追試した
（`compose.yaml` の検証環境。Pleasanter 1.5.7.0）。

日付列に何を送ると何が起きるかを、作成時と編集時の両方で確かめた。

| 送るもの | 作成したとき | **既に値がある行を編集したとき** |
| --- | --- | --- |
| キーごと送らない | 未設定（`1899-12-30`） | ⚠️ **前の値が残る**（消せない） |
| `"DateA": null` | ❌ **`400 Invalid json data`** | ❌ **`400 Invalid json data`** |
| `"DateA": "0001-01-01T00:00:00"` | 未設定（`1899-12-30`） | **未設定へ戻る** |
| `"DateA": "1753-01-01T00:00:00"` | 未設定（`1899-12-30`） | （同上） |
| `"DateA": "1899-12-30T00:00:00"` | 未設定（`1899-12-30`） | **未設定へ戻る** |

**`1899-12-30` より前の日時は、送っても未設定として保存される。**
SQL Server の `datetime` の下限（`1753-01-01`）を送っても同じだった。

**数値列は `null` を送れる**（`NumHash` に `null` を入れた `Update` は `200` で通り、
読み直すと `0` になる）。**`400` になるのは日付列だけ。**

**設計への影響。** **未回答の日付は `DateTime.MinValue`（`0001-01-01T00:00:00`）を送る。**

- `null` は送れない（送信そのものが落ちる）
- キーごと送らない方式は、**編集で回答を消したときに前の値が残る**ので採らない
- ⚠️ **一覧では `1899-12-30` に見え、「1899-12-30 と回答」と区別できない。**
  未回答だったことは回答の正本 JSON（`DescriptionA` 等）でさかのぼる（5 章）

## 11. `GetSite` の `SiteSettings.Columns` に項目名（`LabelText`）が載る（2026-10-10・Pleasanter 1.5.8.1）

`CreateSite` で `LabelText` を付けた列は、`GetSite` の応答の `Response.Data.SiteSettings.Columns` に
`ColumnName` と並んで返る。マッピング画面が割り当て先の項目名を出すのに使う（Issue #549）。

```json
[{"ColumnName":"ClassA","LabelText":"回答GUID"},{"ColumnName":"ClassB","LabelText":"満足度"},
 {"ColumnName":"DateA","LabelText":"来店日"},{"ColumnName":"NumA","LabelText":"点数"}]
```

- 再現は `tools/pleasanter-testenv` の `docker compose run --rm verify`（`results/getsite.json`）
- **編集画面の名前（`LabelText`）と一覧の名前（`GridLabelText`）は別々に返る。** 片方だけ付けた列は、付けた方だけが載る
  （`ClassA` に両方、`ClassB` に `LabelText` だけ、`ClassC` に `GridLabelText` だけを付けて確認）
- **名前を付けていない列（`ColumnName` だけ）は応答の `Columns` に載らない。**
  本アプリは空と物理名と同じものを「名前なし」として扱う
- **設定を初期化した列も `Columns` から消える。** 名前を付けた列の設定を空に戻して `UpdateSite` すると、
  その列は次の `GetSite` に載らない（`ClassA`〜`ClassD` のうち `ClassC` を初期化したら `ClassA`・`ClassB`・`ClassD` だけが返った）。
  **したがって `Columns` の件数は「使える列の本数」ではない。** Issue #551
- **リンクの指定は 2 通りある。**
    - **行の形:** `ChoicesText` の `[[サイト ID]]` の行（`[[1,NoAddButton]]` のように options を続けられる）。
      通常の選択肢の行と混在できる。**`Link: true` が付く**
    - **JSON の形:** `ChoicesText` 全体が `[{"SiteId":1,"NoAddButton":true,"Priority":1},{"SiteId":2}]` のリンク定義の配列。
      **`Link: true` は付かない**（`Link` だけではリンクと見分けられない。2026-10-10 実測）。
      本体のソースでは `ChoicesText` を `List<Link>` として読み、読めたら JSON の形のリンクとして扱う
      （`SiteSettings.cs` の `SetLinks`）
- **選択肢は `ChoicesText`**（1 行 1 件。`値,表示文字列`）。`ChoiceHash` は載らない（2 章）。
  **選択項目にするには選択肢を入れる。** 見せ方は `ChoicesControlType`（`Radio` など）

```json
[{"ColumnName":"ClassA","LabelText":"部署","ChoicesText":"1,営業\n2,開発\n3,総務","ChoicesControlType":"Radio"},
 {"ColumnName":"ClassB","LabelText":"取引先","ChoicesText":"[[1]]","Link":true},
 {"ColumnName":"ClassD","LabelText":"選択肢とリンク","ChoicesText":"1,AAA\n[[1]]","Link":true}]
```

### 12.4 仕様書の前提との照合

**仕様書の決定と矛盾して止めるべきものはなかった**（U6・U8・U11 の前提は成り立つ）。
ただし次の 3 点は、**「定義の検証」（#804 の手順 2）が受け付ける列の型を決めるため、実装の前に人の判断が要る**。

1. **完全一致の意味は DB の照合順序に従う。** SQL Server（Pleasanter の `Japanese_90_CI_AS_KS`）では大文字小文字・全角半角・末尾空白を区別せず、
   `ABC-001` の検索で `abc-001`・`ＡＢＣ-００１` の別レコードも候補になる。PostgreSQL は区別し、MySQL は中間。
   仕様書は「完全一致」としか書いていない。
    - 選択肢 A: **Pleasanter の挙動のまま受け入れ**、運用文書に「参照元の DB の照合順序に従う。キーの表記ゆれのない参照元を使うこと」と書く
    - 選択肢 B: 取得した候補をアプリ側で厳密に絞り直す（正規化・大文字小文字の扱いの仕様が別途要る）
    - **推奨: A。** 参照元マスターは管理者が用意する公開用の別サイトで、表記ゆれがあっても複数候補のモーダルで人が選べる（仕様どおり）。
      B は「検索都合の正規化をしない」という 5.3 節の決定と衝突しうる
2. **数値列は既定で 0 を保存・返却できない**（`Nullable` を設定した列だけ 0 を持てる）。ゼロを返却値として入力先の数値項目へ写したい参照元は、
   **列の設定 `Nullable: true` が要る**。
    - 選択肢 A: 返却を許可する数値列に `Nullable: true` を要求し、`GetSite` で確認できなければ有効化を拒否する
    - 選択肢 B: 要求せず、「0 は空と区別できず反映されない」と管理画面に警告する
    - **推奨: A。** 手順書 2.1 は返却数値の 0 を試験データに挙げており、反映されない状態を黙って許すと、仕様書 1 章（取得値が空なら変えない）と食い違って見える
3. **キーにできる参照元の列の型を絞る必要がある。** 条件が**黙って捨てられて全件が返る**型・値が実在した
   （選択肢のある列の単一の文字列、数値列の整数以外、空文字）。仕様書 5.3 の「安全な単一値条件を作れない列型・値は明示エラー」の対象が具体になった。
    - 選択肢 A: **キーの参照元の列は、選択肢のない文字列の列と、整数に読める値だけの数値列に限る**。選択肢のある列・日付・チェックは初期対象外とし、定義の保存時に拒否する
    - 選択肢 B: 選択肢のある列も、サーバーが `["値"]` の 1 要素の配列を生成して許す（3 DB で効くことは確認した）
    - **推奨: A。** 仕様書は「キーは 1 行テキスト・数値」で、選択肢のある列は想定にない。B は後から足せる

その他、実装へ渡す事実（判断は要らない）:

- 空のキー・NUL を含む値は、DB によって「条件が捨てられる」「切り詰められる」「HTML のエラーになる」と挙動が割れる。
  **仕様書どおり、外へ出す前にアプリ側で拒否する**
- 権限なしと不存在はともに 404、正常な 0 件は 200・`TotalCount=0`。**0 件と接続・権限不備は区別できる**
- 統合・継承の検出は、専用ユーザーの `GetSite` で足りる（`IntegratedSites` が空でなければ拒否、`InheritPermission` が自サイト ID でなければ拒否）。
  統合は**専用ユーザーが読める別サイトまで**範囲を広げ、読めないサイトは漏らさない。継承は親の権限を自動で引く
- 応答の大きさは `Class` 10 列×21 件の最悪で約 0.6 MB。`DescriptionA` のような長文列を許可列に含めると上限が見えなくなる（2 万文字×21 件で 1.8 MB）。
  **応答サイズの有限上限の採用値（目安として 1 MiB）と、許可列に長文列を含める扱いは、手順 3（読み取り）の実装時に決める**
